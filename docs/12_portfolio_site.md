# 12 – The portfolio site (Phase 6d)

> One GitHub Pages site that shows the whole project: the story, one chapter per phase, the BI pages and
> the dbt docs. It is published by the production pipeline itself, after every merge, so nothing on it is
> drawn by hand or can drift from what is running.

---

## 0. The big picture

```
merge to main
   │
   ▼
Deploy production (deploy.yml)
   ├─ job deploy   dbt build (prod) ─► delivery gate ─► dbt docs generate --static ─► artifact prod-state
   │                                                                                  (manifest, catalog,
   │                                                                                   static_index.html …)
   └─ job site     download prod-state
                   ├─ tools.lineage.collect --current + render   lineage pictures from THIS manifest
                   ├─ bi/:   npm ci && npm run build            the 6 BI pages            ─► bi/dist
                   ├─ site/: npm ci && npm run build            home + 11 chapters        ─► site/dist
                   ├─ tools.site.assemble                       site/dist + bi/dist + docs ─► _site/
                   └─ upload-pages-artifact + deploy-pages      ─► https://calvinwang-3333.github.io/balenciaga-pricing-pipeline/
```

| Path on the site | Built from | Tool |
|---|---|---|
| `/` and `/phase-0` … `/phase-6d` | `site/src/*.md` | Observable Framework |
| `/bi/` | `bi/src/*.md` on the snapshot in `bi/src/data/` | Observable Framework |
| `/dbt-docs/` | `dbt docs generate --static` in the production run | dbt |

Pull requests run a third CI job, **BI pages and site build**: no warehouse, no secret, it renders the lineage
from the committed graphs and builds both sites. A page that does not build is caught before the merge.

## 1. The method: design for the reader, the same way as the BI pages

**Plain.** A shop window is arranged for the person walking past, not for the warehouse. A recruiter gives the
window two minutes; a friend outside data needs every number explained; a technical interviewer wants to check
the claims. Each of them needs a different door into the same shop.

**Professional.** The BI pages were decomposed question → decision → grain → model → guarantees → chart
(chapter 11). The site uses the same idea one level up: **reader → their question → the evidence → the page**.

| Reader | Their question | Where the site answers it |
|---|---|---|
| Recruiter, 2 minutes | What did this person solve? | Home: the incident in three lines, before and after |
| Friend outside data | What does any of it mean? | *In numbers*: every figure has a plain sentence, then a small technical line; every chapter opens with a plain lede |
| Analytics engineering interviewer | How did they decide? | The chapters: problem, decision, **rejected alternatives**, dbt features, lineage, proof |
| Engineer checking the claims | Is it real? | dbt docs from the production run, lineage from its manifest, the repository and its CI runs |

### The chapter template, enforced by code

Every phase page has the same six sections, in the same order:

| # | Section | What it holds |
|---|---|---|
| 01 | Problem | the concrete problem of the phase, in plain words first |
| 02 | Decision | what was decided, usually with one table (models and grain, environments …) |
| 03 | Rejected | the alternatives considered and why not: the part that shows judgement |
| 04 | dbt features | each feature used and what it does *here*, plus one real snippet from the repo |
| 05 | Lineage | the DAG when the phase was merged, compiled from git |
| 06 | Proof | the numbers of the reference run |

The header (headline, plain lede, merged PR and commit, nodes before → after, result, what it adds, link to the
full chapter), the lineage section and the previous/next links are generated by
`site/src/components/chapter.js` from **one table of facts per phase** in `site/src/data/phases.js`. A chapter
cannot forget its header or put its lineage in a different place: the structure is code.

## 2. The design system

Balenciaga-*inspired*, not Balenciaga: no logo, no wordmark of the brand, and every footer says it is an
independent portfolio project on synthetic data, not affiliated with the brand.

| Element | Choice | Why |
|---|---|---|
| Background | concrete grey `#E4E4E1` | shared with the BI pages and the lineage pictures |
| Display type | **Archivo at its widest setting** (`font-stretch: 125%`), weight 900, uppercase | the very wide, extra-heavy capitals of luxury fashion branding, with a free font |
| Labels | 11 px uppercase, wide letter-spacing | the small utility text of a fashion e-shop |
| Figures | JetBrains Mono, tabular numbers | numbers line up |
| Phase index | a product grid: grey plates with a huge phase number, a DAG bar like a price | reads like a collection, scans like a list |
| Colour | black and greys only; red only for a BLOCKed delivery | colour means one thing |
| Mobile | wide charts and lineage keep their size and scroll inside their own frame | the page itself never scrolls sideways |

The BI pages (`bi/src/style.css`) now use the same display face, so `/` and `/bi/` read as one site.

### The `.gitignore` bug this phase fixes

The first line of `.gitignore` was `data/`, meant for the generator's output at the repository root. Without a
leading `/`, git applies it to **every** folder named `data`, at any depth. When Phase 6c moved the snapshot to
`bi/src/data/`, `git add -A bi` silently skipped it, and the 6c merge removed the snapshot from `main`. The
BI pages still built on your Mac (the files were on disk), so nothing failed.

`/data/` matches only the root folder. This PR adds the 11 snapshot files back. The new CI job would have caught
it: it builds the BI pages from a clean checkout, where missing data fails the build.

**Lesson:** an ignore rule without `/` is global. A CI job that builds from a fresh clone is what catches "works on
my machine".

## 4. Your steps

> zsh-safe: one command per line, no `#` comments. Run from the repository root.

### Step 1 – a branch for 6d

The files are already in your folder (Claude wrote them). Your current branch, `phase-6c/bi-pages`, has exactly
the same files as `main`, so branch from where you are:

```bash
git switch -c phase-6d/site
git status
```

You should see the site files as new, the lineage pictures as moved, and `bi/src/data/` (11 files) as new.

### Step 2 – install the two workflow files

```bash
mv ci/ci.yml.next .github/workflows/ci.yml
mv ci/deploy.yml.next .github/workflows/deploy.yml
git diff --stat .github
```

### Step 3 – turn on GitHub Pages (once)

GitHub → the repository → **Settings → Pages → Build and deployment → Source: GitHub Actions**. Nothing else.
The first deploy creates the `github-pages` environment by itself.

### Step 4 – preview locally

Node 20 or later (`node -v`).

```bash
cd bi
npm ci
npm run build
cd ../site
npm ci
npm run build
cd ..
python -m tools.site.assemble
python -m tools.site.preview
```

Open http://127.0.0.1:8000. Click through the home page, a chapter, `/bi/`, and the chapter pager. `/dbt-docs/`
shows a placeholder locally; production fills it. Stop with `Ctrl+C`.

For editing a chapter with live reload: `cd site` then `npm run dev` (links to `/bi/` and `/dbt-docs/` 404
in that mode: they only exist after assembly).

### Step 5 – tests, commit, PR

```bash
python -m pytest tools/tests agent/tests qa/tests
ruff check .
git add -A site bi tools ci .github docs .gitignore README.md
git status
git commit -m "feat(site): portfolio site with one chapter per phase, published by the production deploy"
git push -u origin phase-6d/site
```

Open the PR into `main`. Three checks run: the two required ones, plus **BI pages and site build**. No dbt
model changed, so Slim CI builds nothing.

### Step 6 – merge and watch the deploy

After the merge, **Actions → Deploy production** runs two jobs: `deploy` (as before) then `site`. The `site`
job's summary shows the Pages URL. Open it and check `/`, `/phase-4`, `/bi/micro` and `/dbt-docs/`.

Optional: add **BI pages and site build** to the required checks of the `main` ruleset (Settings → Rules).

**Checkpoint – Phase 6d is done when:**
- [ ] the site is live at `https://calvinwang-3333.github.io/balenciaga-pricing-pipeline/`
- [ ] `/dbt-docs/` shows the production docs, and a model card link on `/bi/micro` opens the right model
- [ ] the home page lineage shows 58 nodes
- [ ] `git ls-files bi/src/data | wc -l` says 11

Then sync your local `main`: `git switch main` and `git pull`.

## 5. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `site` job: "Get Pages site failed" | Pages source not set | Step 3 |
| `site` job: "Branch main is not allowed to deploy to github-pages" | environment protection rules | Settings → Environments → github-pages → allow `main` |
| `npm ci` fails on the lock file | `package.json` edited without `npm install` | `npm install` in that folder, commit both files |
| BI build fails: file not found `data/…csv` | the snapshot is not in git | `git ls-files bi/src/data`; see the `.gitignore` fix |
| a chapter shows a broken table or raw markdown | a missing blank line inside `<div class="content">` | keep a blank line after the opening tag and before `</div></section>` |
| `sql` code block tries to load DuckDB | Framework runs ```` ```sql ```` blocks | use ```` ```pgsql ```` for display-only SQL |
| headings in Helvetica | offline: Google Fonts unreachable | cosmetic |
